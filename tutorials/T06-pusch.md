# T06 PUSCH协议：从参数、算例到接收代码

## 1. 任务关系、版本与学习边界

协议回答UE（User Equipment，用户设备）怎样构造信号及按何配置发送；基站需要根据同一配置识别资源、产生参考和恢复数据。接收算法可由实现选择，不能把MMSE（Minimum Mean Square Error，最小均方误差）检测或某个LDPC算法说成标准唯一要求。

教学参考：TS（Technical Specification，技术规范）38.211/212/214 V17.9.0 Release 17；项目版本待导师确认。三个月必学目标PUSCH所需条款、资源/参考/编码/调度映射、下列限定算例。全部重复类型、configured grant（配置授权）、跳频、复杂UCI和多slot TB处理后续按项目支持范围深入；公司要求全覆盖时不能自行删减。

前置T02、基础调制编码。每次读条款先问：解决什么问题、输入是谁配置的、输出哪个参数、适用条件是什么、接收端如何使用、哪个用例能验证。

## 2. 38.211：信号如何占据资源

通信问题是让双方一致理解bit、调制符号、层、端口和RE位置。入口为编码bit和调度/参考配置，输出为天线端口资源上的复数符号。阅读[38.211 §6.3.1及§6.4.1.1](https://www.etsi.org/deliver/etsi_ts/138200_138299/138211/17.09.00_60/ts_138211v170900p.pdf)：§6.3.1.1加扰、.2调制、.3层映射、.4变换预编码、.5预编码、.6虚拟资源映射；§6.4.1.1是PUSCH DM-RS。具体信号生成公式和位置表用该版本PDF核对，不只按章节标题实现。

接收对应关系：根据配置定位数据与DM-RS；生成同参考用于信道估计；结合有效信道检测层；软解调得LLR；按相同加扰序列调整软bit符号。启用transform precoding（变换预编码）时链路不同，不能所有用例都当CP-OFDM（Cyclic-Prefix OFDM，带循环前缀OFDM）。

教学配置限定为正常CP、单层、无跳频、关闭变换预编码和PT-RS、无UCI、mapping type A、首DM-RS在symbol2、单symbol DM-RS、无额外DM-RS、type1且两组CDM（Code Division Multiplexing，码分复用）group without data。分配从symbol2起10个symbol、12 PRB。这个例子的DM-RS无数据占用按每PRB12 RE扣除；两组无数据不等于使用两层。真实DM-RS表还受长度、type、ports和额外位置影响。

读代码时找DM-RS位置mask、参考序列初始化、RB起点相对BWP（Bandwidth Part，带宽部分）或载波的位置、层与端口表。把协议配置值与内部枚举/单位并排写，避免起点多加或少加BWP偏移。测试：无噪参考数据、已知资源、DM-RS位置校验、不同合法allocation，先在参考点验证再看CRC。

## 3. 38.214：分配、MCS、TBS与处理约束

输入为grant（授权）及高层配置，输出是时间/频率资源、调制阶数Qm、目标码率R、TBS（Transport Block Size，传输块大小）等。阅读[38.214第6章](https://www.etsi.org/deliver/etsi_ts/138200_138299/138214/17.09.00_60/ts_138214v170900p.pdf)：§6.1.1传输方案、§6.1.2资源、§6.1.3变换预编码、§6.1.4.1调制/码率、§6.1.4.2 TBS、§6.4 UE准备时间。准备时间不是直接给项目每个L1函数规定budget。

单slot适用路径先计算每PRB的`N_RE'=12*L-N_DMRS-N_oh`，再`N_RE=min(156,N_RE')*n_PRB`；§6.1.4.2指向§5.1.3.2的步骤2—4。资源数、MCS表选择、目标码率不是任选组合；TBS资源计数和实际数据/UCI映射也需区分。

本教学计算用Qm=2、R=0.5作为独立数学输入，不声称对应某个MCS index。上节条件下N_RE'=108、N_RE=1296；单层N_info=1296*2*0.5=1296。小块路径量化粒度2^4，N_info'=1296，查该版本TBS表的下一个不小于它的值为1320bit。这是限定条件算例，不能取代通用TBS实现。

调度时间域还需理解K2（上行调度到PUSCH的slot偏移）、S/L（起始symbol和长度）、mapping type；混合numerology需按实际规则换算，不做简单同slot加法。频率域可涉及RIV（Resource Indication Value，资源指示值）或bitmap，先验证项目支持的type。接收端用这些参数配置数据长度、Qm和码率；错误MCS表会让看似相同index含义不同。

代码阅读：追踪grant解析→资源表→MCS table选择→TBS→解码配置，核对所有分支条件。测试按MCS表、allocation边界、DM-RS开销和合法支持模式分组，核对实际UE/测试向量参考，不只验证最终吞吐。

## 4. 38.212：从传输块到编码与复用

通信问题是让接收端在有限资源中恢复数据并发现错误。UL-SCH（Uplink Shared Channel，上行共享传输信道）是传输信道，PUSCH是其物理承载，两者不等同。阅读[38.212 §6.2和相关第5章](https://www.etsi.org/deliver/etsi_ts/138200_138299/138212/17.09.00_60/ts_138212v170900p.pdf)：TB CRC→base graph选择→分段/CB CRC→LDPC→速率匹配→拼接→数据控制复用。UCI（Uplink Control Information，上行控制信息）会改变资源和软bit拆分。

该参考版本TB载荷A>3824时使用CRC24A，否则CRC16；BG（Base Graph，基图）2条件为A≤292，或A≤3824且R≤0.67，或R≤0.25，否则BG1。本例A=1320、R=0.5，得到16bit TB CRC、B=1336、BG2。这些规则的初传/重传上下文必须保留；重传不要随意重新选基图。

分段将大TB拆为CB（Code Block，码块）；lifting size（提升尺寸）Zc决定矩阵展开和buffer规模。filler bit（填充位）、首部puncturing（打孔）和速率匹配不是同一概念。RV决定循环buffer读取起点；重复发送的soft bit在接收端按位置合并，缺失位置与已知填充位置的LLR初始化含义不同。

接收流程需先按配置拆出数据/UCI软bit，逆交织/速率恢复、HARQ合并、解码、CB/TB校验；某些操作可融合，不能靠物理函数顺序判其协议错误。LLR符号约定如“正值支持0”须从项目确认。建议用已知bit、无噪链路和不同RV验证每个映射阶段。

## 6. 实验、常见问题与分析

运行`python3 labs/nr_example.py`，预期输出资源算例、TBS1320、B1336和BG2；程序明确只算本例，不实现完整标准。改PRB或R时不要继续使用脚本固定TBS片段当通用表；改用规范完整分支/表并手工核验。项目实践选两个已通过用例，分别填写版本、grant、资源、Qm/R/TBS、DM-RS、BG/Zc/RV、soft bit长度、输出CRC，定位每个值的真实代码路径。

CRC失败先检查输入配置/IQ质量，再定位最早与参考分歧的中间点。TBS不符查MCS表、开销、量化和分支；LLR长度错查层、资源、UCI及puncture；首传过重传错查HARQ key、RV与buffer复用；高MCS才失败查缩放/饱和、噪声估计和检测质量。

## 7. 自测与三级标准

问：A=1320、R=0.5的CRC/BG？答：CRC16、BG2，B=1336。问：MCS index能独立确定Qm吗？答：还要表选择和适用条件。问：发射标准是否指定基站MMSE？答：不等同接收算法要求。问：为什么能引用214的第5章算TBS？答：该PUSCH条款明确引用步骤，不能任意套用其他下行条件。
